# 10. Контуры и среды

Статус: набросок (09.11.2026). Правила ENV-1..12. Метки: есть / частично / цель.

## Опора

- ADR-0001 (устав): порядок правоты Accepted ADR → канон → шаблоны/схемы.
- `docs/concept.md`: отложенные идеи «политика агентов», «проверка после развёртывания с откатом», «пресеты по типу проекта».
- Смежные области: `02-config` (переменные и секреты), `03-logging-errors` (поля логов), `06-ci-cd` (пайплайн, доставка, релиз), `09-data-model` (классы данных).
- Машинный источник правды: `10-contours/contours.yaml`, схема `10-contours/contour-registry.schema.json`. Этот файл — единственный нормативный текст области; файлы в `10-contours/` описывают подробности и новых правил не вводят.

## Термины

| Термин | Что это | Пример |
|---|---|---|
| Контур | Физическое место запуска с одной зоной доверия | рабочий ПК `cnt` |
| Узел | Машина контура (физическая, VM, рабочая станция, VPS) с ОС, ресурсами, адресами и доказательством | `frm-appsrv` |
| Стадия | Роль в пути к продакшену: `dev`, `test`, `prod` | `dev` |
| Среда | Контур × стадия; единица адресации | `cnt.dev` |
| Релиз | Идентификатор выпуска проекта, не зависит от среды | `release_id` |
| Артефакт | Неизменяемый образ или бандл, идентифицируется digest | `sha256:…` |

## Правила

**ENV-1.** Контуры описаны в одном реестре Angainor (`10-contours/contours.yaml`). Проза и проекции ссылаются на реестр, а не дублируют его. Метка: цель.

**ENV-2.** Код контура: ровно три строчные латинские буквы. Код не меняется и не переиспользуется после вывода контура из эксплуатации. Код не несёт смысла, который может устареть (расположение, владелец, роль). Метка: цель.

**ENV-3.** Стадия — отдельная ось с закрытым списком `dev` / `test` / `prod`. Среда записывается как `<контур>.<стадия>`, например `cnt.dev`. Метка: цель.

**ENV-4.** Среда, релиз и артефакт — три независимые оси. Среда адресуется только своим кодом и везде одинаково: значение переменной `<PROJECT>_ENV`, поле `env` в логах, имя compose-проекта `<project>-<контур>-<стадия>`, аргумент CLI. Релиз идентифицируется `release_id`, артефакт — digest. Один и тот же digest продвигается между средами без изменения идентичности, а журнал выкладки фиксирует тройку (среда, `release_id`, digest). Метка: цель.

**ENV-5.** Карточка контура содержит обязательные поля: роль, владелец, статус, стадии, зона сети и доступ, доставка (CI и способ), допустимые классы данных, хранилище секретов, права агентов и узлы. Факты узла (ОС, ресурсы, адреса) сопровождаются доказательством: статус, источник, дата. Неизвестное записывается явно как `unknown`, не означает разрешения и недопустимо в режиме `approved`. Метка: цель.

**ENV-6.** Допустимые классы данных заданы списком для каждого контура. Всё, что не разрешено явно, запрещено; пустой список означает запрет. Класс данных проекта фиксируется в его pin и в `data-model.yaml`. Метка: цель.

**ENV-7.** Путь продвижения — явный список переходов между средами с указанием способа доставки. Перехода, которого нет в списке, не существует. Метка: цель.

**ENV-8.** Секреты не попадают в Git и в поставку (образы, бандлы, манифесты, логи). Каждая среда получает свои учётные данные из хранилища своего контура; общий внешний сервис может иметь отдельные ограниченные учётные данные в нескольких средах, выданные управляемым процессом. В репозитории только имена секретов и ссылки на них. Метка: цель.

**ENV-9.** Права агентов задаются на контур: список разрешённых инструментов и режим человека в контуре. По умолчанию запрещено. Здесь описана dev-time политика; runtime AgentPolicy (ENTAN) — отдельный документ. Метка: цель.

**ENV-10.** Проект фиксирует среды, в которых живёт, и версию реестра в pin `docs/architecture/contours.yaml`. Проверка сверяет pin с реестром. Pin среды `prod` ссылается на реестр в режиме `approved` и на существующий git-тег. Метка: цель.

**ENV-11.** Для среды со стадией `prod` бэкап и проверка после выкатки доказуемы, а не декларированы. Для бэкапа заданы объект, расписание, retention, RPO/RTO, дата последнего восстановления и его результат; проверка после выкатки имеет исполняемую пробу. Допустим явный отказ с причиной. `required: true` без этих полей не считается выполнением. Метка: цель.

**ENV-12.** Таблица контуров в README, раздел AGENTS.md «где что запускать, чего нельзя», матрица CI и список переменных — проекции реестра. Руками не правятся, дрейф ловит проверка. Метка: цель.

## Зачем

Проверка здравого смысла: «написал → выкатил на `<код>`» должно однозначно определять цель, стадию, способ доставки, допустимые данные и права агентов. Без реестра эти знания живут в голове владельца и расходятся между проектами. Разделение контура и стадии не даёт смешивать «где» и «насколько боевое». Данные и права агентов вынесены в карточку, потому что именно они различают контуры по риску, а не по железу. Статус доказательства различает проверенное и предполагаемое, а `unknown` не даёт принять отсутствие сведений за разрешение.

## Как проверяется

Цель: `scripts/check_contours.py` (в ядре Angainor).

- реестр валидируется по `contour-registry.schema.json`; в режиме `approved` нет `open_items`, нет значений `unknown`, у каждого контура есть стадии и узлы;
- перекрёстные ссылки, которые JSON Schema не выражает: `allowed_data_classes` ⊂ `data_classes`, `promotion` ссылается на существующие среды, `parent_node` существует, id узла начинается с кода своего контура, коды уникальны, адреса со статусом `current` не повторяются;
- для `prod`-контура заполнены поля backup и post_deploy_check (ENV-11);
- код из предыдущего git-тега не исчезает и не меняет смысл, код `retired` не переиспользуется (ENV-2);
- pin проекта валидируется по `contours-pin.schema.json` и сверяется с реестром; pin `prod` ссылается на `approved` и существующий тег (ENV-10);
- проекции пересобираются и сравниваются с закоммиченными (ENV-12).

Пока проверки нет, `check_canon_links.py` проверяет только связность кодов ENV-* с подробными файлами; реестр и схема сверены разовым минимальным валидатором.

## Открытые вопросы

1. Неподтверждённые факты и незаполненные поля ведутся как `unknown` и `open_items` в `contours.yaml`. Первыми закрыть: топологию `frm` и адреса `.30`/`.140` (OI-01), размещение раннера на `cnt` (OI-02), данные о Moexlab (OI-03), классификацию данных (OI-05), ротацию учётных данных из карточки Pharos (OI-07). Код Moexlab (`mxl`) — предложение.
2. Классы данных: стартовый список в реестре (`synthetic`, `public`, `own`, `licensed`, `employer`) — подтвердить или заменить. Отдельно решить, как учитывать лицензионные условия рыночных данных.
3. Префиксы переменных: ENV-4 предлагает один вход `<PROJECT>_ENV=<контур>.<стадия>` вместо префикса по коду контура. Согласовать с областью 02-config (CFG-*).
4. Различаются ли допустимые данные и права агентов по стадиям внутри одного контура. Сейчас поля на уровне контура.
5. Нужен ли отдельный контур под стадию `test`, или `test` — стадия на уже существующих контурах.
6. Доставка в Moexlab: образы идут по почте. Нужны формат бандла (манифест с версиями и sha256, проверка при приёме), решение по зависимостям без интернета (локальное зеркало, колёса в образе), подпись манифеста (кто держит ключ и где лежит публичный на приёмной стороне) и подтверждение, что политика работодателя допускает такой канал.
7. Адреса в реестре: публичный IP VPS (`prs`) лучше не хранить в репозитории, который может стать публичным. Варианты: оставить только приватные адреса, а публичные держать в инвентаре контура вне git.
8. Место схем: `contour-registry.schema.json` лежит рядом с реестром, остальные схемы — в `schemas/`. Выбрать одно место.
9. ADR на схему именования контуров (Proposed), в одном ряду с форматом ADR и префиксами; номер назначить.
