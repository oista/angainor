# 04. Тесты

Какие тесты пишутся, где лежат и что считается проверенным.

**Опора:** [пирамида тестов](https://martinfowler.com/articles/practical-test-pyramid.html) (M. Fowler) — много быстрых unit-тестов, меньше интеграционных, мало сквозных; схема теста «Подготовка → Действие → Проверка» (Arrange-Act-Assert); [карантин нестабильных тестов](https://martinfowler.com/articles/nonDeterminism.html); сверка с эталонными файлами (golden / snapshot testing).

## Правила

**TST-1.** Три уровня тестов. Unit — быстрые, без сети и базы данных, их большинство. Integration — с настоящей базой в контейнере (в CI Postgres поднимается как сервис), помечаются `@pytest.mark.integration`. Сквозные (e2e) — только для веб-интерфейса, через Playwright. *(частично)*

↳ Шаблон: [`tests/integration/test_example_integration.py`](../../templates/tests/integration/test_example_integration.py)

**TST-2.** Новая логика приходит с тестом в том же PR. Исправление ошибки приходит с тестом, который падал до исправления. *(частично)*

**TST-3.** Каждое правило и каждый инвариант проверяются парой примеров: один должен пройти, другой — упасть. Правило без падающего примера считается непроверенным. *(частично)*

↳ Шаблон: [`tests/unit/test_example.py`](../../templates/tests/unit/test_example.py)

**TST-4.** Архитектурные правила оформляются как обычные тесты в `tests/architecture/`: границы импортов, отсутствие запрещённых зависимостей, соответствие документации коду. *(частично)*

↳ Шаблон: [`tests/architecture/test_no_print.py`](../../templates/tests/architecture/test_no_print.py)

**TST-5.** Сгенерированные файлы сверяются с эталоном (golden-файлом). Эталон обновляется осознанно, отдельной командой, и изменение видно в PR. *(частично)*

**TST-6.** У каждого теста есть ограничение по времени (`pytest-timeout`), самые медленные тесты видны в отчёте (`--durations`). *(частично)*

↳ Шаблон: [`pyproject.toml`](../../templates/pyproject.toml)

**TST-7.** Нестабильный тест переносится в `tests/unit/quarantine/` с указанием причины и не блокирует CI. Карантин регулярно разбирают, а не копят. *(частично)*

**TST-8.** Тест читается как «Подготовка → Действие → Проверка». Внешние системы заменяются подставными объектами (моками). Тест без проверки (`assert`) запрещён. *(частично)*

↳ Шаблон: [`tests/unit/test_example.py`](../../templates/tests/unit/test_example.py)

**TST-9.** Тестовые данные лежат в `tests/fixtures/`, а не внутри кода теста и не скачиваются из сети. *(частично)*

## Зачем

Быстрые тесты запускают часто, медленные — редко. Если основа — unit-тесты, обратная связь приходит за секунды, в том числе агенту между правками. Тест, который никогда не падал, ничего не доказывает: пара «проходит / падает» показывает, что проверка действительно ловит нарушение. Эталонные файлы делают видимыми непреднамеренные изменения в сгенерированном. Карантин не даёт одному нестабильному тесту приучить всех игнорировать красный CI.

## Как сейчас

| Проект | Как сделано |
| --- | --- |
| PRODATA | 166 файлов unit-тестов; integration с Postgres 16 в CI; карантин `tests/unit/quarantine`; ограничение 45 с на тест; сборка и тесты фронтенда через npm |
| moex-data-model | тесты в каждом пакете и `tests/architecture` (границы импортов, уникальность номеров ADR); сверка с эталоном (`compare_golden.py`); e2e через Playwright; у 67 инвариантов обязательны пары примеров (ADR-045) |
| Clavis | плоский `tests/` с fixtures, тесты API, SPARQL и SHACL |
| Norma | тесты коннекторов `norma-canalis` |

Расхождения: покрытие кода тестами не измеряется ни в одном проекте. Требование пары «проходит / падает» формально закреплено только в moex-data-model.

## Как проверяется

- CI запускает unit- и integration-тесты (PRODATA), полный набор через `check_all.py` (moex-data-model), pytest (Clavis, Norma).
- `scripts/check_constraint_matrix.py --gate-strict` (moex-data-model) — у инварианта со статусом `implemented` есть оба примера.
- TST-2 и TST-8 — на ревью.
