# 03. Логи и ошибки

Как приложение сообщает о том, что происходит, и что делает, когда что-то идёт не так.

**Опора:** [12-factor, XI. Logs](https://12factor.net/logs) — приложение пишет логи потоком в stdout, а собирает их окружение; [Python Logging HOWTO](https://docs.python.org/3/howto/logging.html) — логгер на модуль, настройка в точке входа; [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457) — машиночитаемый формат ошибок HTTP API; [OWASP Fail securely](https://owasp.org/www-community/Fail_securely).

## Правила

**LOG-1.** В каждом модуле — `logger = logging.getLogger(__name__)`. `print` используется только в CLI для вывода пользователю. *(частично)*

↳ Шаблон: [`src/__pkg__/logging_setup.py`](../../templates/src/__pkg__/logging_setup.py), [`tests/architecture/test_no_print.py`](../../templates/tests/architecture/test_no_print.py)

**LOG-2.** Логирование настраивается один раз, в точке входа (main, CLI). Библиотеки и пакеты сами его не настраивают. *(есть)*

↳ Шаблон: [`src/__pkg__/logging_setup.py`](../../templates/src/__pkg__/logging_setup.py)

**LOG-3.** Приложение пишет логи в stdout/stderr; куда их отправить, решает окружение (Docker, сборщик логов), а не код. Файловые логи допустимы только у локальных утилит. *(частично)*

↳ Шаблон: [`src/__pkg__/logging_setup.py`](../../templates/src/__pkg__/logging_setup.py)

**LOG-4.** В контейнерах логи пишутся по одной JSON-строке на событие: время, уровень, имя логгера, сообщение и идентификатор операции (`run_id` или `request_id`), чтобы все события одной операции можно было собрать вместе. *(цель)*

↳ Шаблон: [`src/__pkg__/logging_setup.py`](../../templates/src/__pkg__/logging_setup.py) · Схема: [`log-event.schema.json`](../../schemas/log-event.schema.json)

**LOG-5.** Пароли, токены, ключи и персональные данные в логи не пишутся. *(частично)*

↳ Шаблон: [`src/__pkg__/logging_setup.py`](../../templates/src/__pkg__/logging_setup.py)

**LOG-6.** Ошибка не проглатывается молча. `except Exception: pass` и `return None` без записи в лог запрещены. Перехваченную ошибку либо осмысленно обрабатывают, либо записывают в лог и передают дальше. *(частично)*

↳ Шаблон: [`src/__pkg__/errors.py`](../../templates/src/__pkg__/errors.py)

**LOG-7.** У каждого пакета есть своя базовая ошибка и несколько наследников по смыслу (например, `OntologyError` → `OntologyLoadError`, `OntologyValidationError`). Ошибки пакета перехватывают по его базовому классу, а не по `Exception`. *(частично)*

↳ Шаблон: [`src/__pkg__/errors.py`](../../templates/src/__pkg__/errors.py)

**LOG-8.** Ошибки, которые видит пользователь или оператор, описаны в каталоге модуля `assets/<module>_errors.json`. Каждая запись: код вида `модуль.область.ИМЯ`, серьёзность, заголовок и подсказка «что делать дальше» на русском и английском, HTTP-статус. Сначала ошибка добавляется в каталог, потом используется в коде. API отдаёт код, заголовок и подсказку, а не трассировку стека. *(частично)*

↳ Шаблон: [`src/__pkg__/assets/example_errors.json`](../../templates/src/__pkg__/assets/example_errors.json) · Схема: [`error-catalog.schema.json`](../../schemas/error-catalog.schema.json)

**LOG-9.** Ошибка, которой нет в каталоге, получает общий код `platform.UNKNOWN`, а не сырой текст исключения. *(частично)*

↳ Шаблон: [`src/__pkg__/errors.py`](../../templates/src/__pkg__/errors.py)

## Зачем

Текст исключения вроде `Exit code 1` ничего не говорит оператору и агенту: непонятно, что сломалось и что делать. Код ошибки с подсказкой позволяет и человеку, и агенту действовать без чтения исходников. Тихо проглоченная ошибка выдаёт сбой инфраструктуры за плохой результат — это уже приводило к неверным выводам в оценке качества (ADR-0041 PRODATA). Идентификатор операции в логах — единственный способ восстановить ход одного запуска среди тысяч строк.

## Как сейчас

| Проект | Как сделано |
| --- | --- |
| PRODATA | стандартный `logging` с текстовым форматом через `basicConfig`; каталоги ошибок в 9 модулях (ADR-0006); запрет «тихих» ошибок проверяется только на границах доверия (правило R-005) |
| moex-data-model | стандартный `logging`, свои классы ошибок в пакетах |
| Clavis | иерархия ошибок `ontology_core/errors.py` |
| Norma | агентский рантайм пишет структурированную запись хода (`TurnRecord`) |

Расхождения и пробелы: логирование — самое слабое место всех проектов. JSON-логов и идентификаторов операций нет нигде. В коде PRODATA 149 мест с `except Exception:`; не все они плохие, но проверка R-005 покрывает только границы доверия.

## Как проверяется

- Правило R-005 archpolicy (PRODATA) — нет тихих ошибок в модулях на границах доверия.
- `scripts/check_error_catalog_coverage.py` (PRODATA) — коды ошибок из кода есть в каталогах.
- Формат логов и отсутствие `print` не проверяются.

## Открытые вопросы

- Общая функция `configure_logging(json: bool)` для всех проектов: в Norma или в шаблоне Angainor.
- Распространить R-005 на весь код с «храповиком»: число нарушений зафиксировано и может только уменьшаться (см. QLT-2).
