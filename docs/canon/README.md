# Канон практики

Канон описывает каркас, который повторяется в каждом проекте: как устроен репозиторий, как задаётся конфигурация, как пишутся логи и ошибки, как тестируется код, какие проверки качества запускаются, как устроены CI/CD, документация и архитектурные решения. Отдельный файл — архитектурные приёмы, которые прижились в нескольких проектах и доказали пользу.

Канон фиксирует то, что уже работает, а не идеал. Где проекты расходятся, это отмечено, а выбор выносится в meta-ADR Angainor.

Состояние на 09.11.2026. Источники: PRODATA (`moex-prodata-platform`), `moex-data-model`, Clavis (`cavis`), Norma.

## Для кого и как читать

Канон читают инженеры и ИИ-агенты.

- Правила в разделе «Правила» обязательны для нового кода во всех проектах.
- Проект может отступить от правила только своим Accepted ADR, в котором прямо названо, какое правило отменяется и почему.
- У каждого правила есть код (`CFG-3`, `TST-2`). Ссылайтесь на код в ADR, PR и комментариях к ревью.
- Метка после правила показывает, насколько оно уже внедрено: **есть** — делается и проверяется автоматически; **частично** — делается не во всех проектах или проверяется вручную; **цель** — принято как норма, но пока не делается.

## Краткие файлы и папки с подробностями

Область описывается в два слоя:

- **Краткий файл** `NN-область.md` — правила с кодами. Его читают первым, он короткий.
- **Папка** `NN-область/` — подробные файлы `NNN-тема.md`, каждый описывает одну тему: из чего она состоит, как оформлять, как проверяется. Подробный файл не вводит новых правил: он ссылается на коды из краткого файла и объясняет, как их выполнить. Новое обязательное требование сначала появляется правилом в кратком файле.

Подробные файлы пишутся по шаблону [_detail-template.md](_detail-template.md). Под правилом краткого файла стоит строка `↳ Подробно: …` со ссылкой на нужный подробный файл.

## Шаблоны и схемы

Правило говорит, что делать и зачем; как это выглядит — показывают шаблоны и схемы. Под правилом стоит строка `↳ Шаблон: … · Схема: …` со ссылками.

- [`templates/`](../../templates/) — шаблоны файлов, разложенные так, как они лягут в новый проект. Позже эта папка станет шаблоном для copier. Заглушки: `__pkg__` — имя пакета, `APP` — префикс переменных окружения проекта, `<project>` и другие `<…>` — текст для замены.
- [`schemas/`](../../schemas/) — машиночитаемые форматы (JSON Schema): запись лога, каталог ошибок, схема переменных, шапка ADR, реестр инвариантов, паспорт модуля.

Каждый шаблон и каждая схема в первых строках объявляет правила, которые воплощает: `canon: DOC-6, DOC-7` (в JSON — поле `$comment`). Связи проверяет [`scripts/check_canon_links.py`](../../scripts/check_canon_links.py): ссылка из правила ведёт на существующий файл, файл объявляет это правило, объявленные коды существуют.

## Как устроен каждый файл

Все файлы написаны по одной схеме:

1. **Опора** — общепринятые инженерные практики, на которых основан раздел. Если правило совпадает с известной практикой, оно не изобретается заново.
2. **Правила** — короткие обязательные нормы с кодом и меткой внедрения.
3. **Зачем** — какую проблему решают правила.
4. **Как сейчас** — как это сделано в проектах сегодня и где они расходятся.
5. **Как проверяется** — какие проверки уже следят за правилами; всё остальное держится на ревью.
6. **Открытые вопросы** — что ещё предстоит решить.

Под правилом может стоять строка `↳` со ссылками на шаблоны и схемы.

## Как менять канон

Изменение правила — PR в angainor с meta-ADR, если правило меняет поведение проектов. Правило и его шаблон меняются в одном PR; `python scripts/check_canon_links.py` должен проходить. Новое правило добавляется, только если оно уже работает хотя бы в одном проекте или закрывает реальный случай, который к чему-то привёл. Цель — со временем у каждого правила появляется автоматическая проверка.
