# 05. Линтеры и качество кода

Какие автоматические проверки следят за кодом до ревью.

**Опора:** [ruff](https://docs.astral.sh/ruff/) — единый линтер Python, объединяет pyflakes, pycodestyle, isort и flake8-bugbear; [mypy](https://mypy.readthedocs.io/) с постепенной типизацией; [import-linter](https://import-linter.readthedocs.io/) — контракты зависимостей между пакетами; [pre-commit](https://pre-commit.com/); «храповик» (ratchet) — в старом коде число нарушений может только уменьшаться.

## Правила

**QLT-1.** Линтер — ruff, длина строки 100, наборы правил `E, F, I, UP, B, BLE`: синтаксис и стиль, неиспользуемый код, порядок импортов, устаревшие конструкции, типичные ошибки, слишком широкий `except`. *(частично)*

↳ Шаблон: [`pyproject.toml`](../../templates/pyproject.toml)

**QLT-2.** Типы. Новый пакет с первого дня проверяется mypy в строгом режиме. В старом коде работает храповик: текущее число ошибок записано в репозитории, CI падает, если оно выросло. *(частично)*

↳ Шаблон: [`pyproject.toml`](../../templates/pyproject.toml)

**QLT-3.** Границы между пакетами проверяет import-linter. Каждый контракт «пакет X не импортирует Y» сопровождается комментарием со ссылкой на ADR, который это требует. *(частично)*

↳ Шаблон: [`.importlinter`](../../templates/.importlinter)

**QLT-4.** Все текстовые файлы — UTF-8, переводы строк зафиксированы в `.gitattributes`. Отдельная проверка ищет «кракозябры» (испорченную кодировку) в русских текстах. *(частично)*

↳ Шаблон: [`.gitattributes`](../../templates/.gitattributes), [`scripts/check_mojibake.py`](../../templates/scripts/check_mojibake.py)

**QLT-5.** Перед коммитом запускается pre-commit: ruff, лишние пробелы, перевод строки в конце файла, корректность YAML, слишком большие файлы. CI повторяет те же проверки — pre-commit только экономит время. *(частично)*

↳ Шаблон: [`.pre-commit-config.yaml`](../../templates/.pre-commit-config.yaml)

**QLT-6.** Исключения из правил линтера — точечные: по пути в конфиге или в конкретной строке, с причиной. Отключать правило для всего проекта запрещено. *(частично)*

**QLT-7.** Ревью проверяет то, что не ловит автоматика: есть ли ADR для архитектурного изменения, обновлены ли документы, добавлен ли тест. Чек-лист лежит в шаблоне PR (`.github/PULL_REQUEST_TEMPLATE.md`). *(частично)*

↳ Шаблон: [`.github/PULL_REQUEST_TEMPLATE.md`](../../templates/.github/PULL_REQUEST_TEMPLATE.md)

## Зачем

Линтер снимает с ревью спор о мелочах и ловит ошибки до запуска. Типы и контракты импортов удерживают границы, которые иначе размываются за несколько месяцев, особенно когда код пишет агент. Храповик позволяет ввести строгую проверку в старый проект без остановки работы: долг больше не растёт и постепенно уменьшается. Проблема кодировки реальна: workflow Norma сохранён в UTF-16, и GitHub его, скорее всего, не читает.

## Как сейчас

| Проект | Как сделано |
| --- | --- |
| PRODATA | ruff `E, F, I, UP`, ограничение длины строки (E501) отключено для всех пакетов; mypy strict только для `gitlab_lineage` — 135 ошибок, в CI не блокирует; import-linter — 7 контрактов со ссылками на ADR; чек-лист PR |
| moex-data-model | линтер схем LinkML (`.linkmllint.yaml`); границы импортов в `tests/architecture/test_import_boundaries.py` |
| Clavis | ruff `E, F, I, B, UP, BLE`; мягкий mypy; pre-commit; проверка кодировки `check_mojibake.py` |
| Norma | линтера в CI нет |

Расхождения: наборы правил ruff разные; ограничение длины строки (E501) отключено и в PRODATA, и в Clavis; pre-commit есть только в Clavis; храповик для mypy описан в документе PRODATA, но не закреплён проверкой.

## Как проверяется

- ruff в CI (PRODATA, Clavis).
- import-linter в CI (PRODATA); `test_import_boundaries.py` (moex-data-model).
- mypy в CI (PRODATA, Clavis), пока не блокирует.
- `check_mojibake.py` (Clavis).

## Открытые вопросы

- Включать ли автоформатирование (`ruff format`): в Clavis оно сознательно выключено из-за шумных диффов.
- Где хранить число для храповика mypy — файл в репозитории, который обновляется только в сторону уменьшения.
