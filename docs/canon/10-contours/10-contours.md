# 10. Контуры и среды

Статус: набросок (09.11.2026). Правила ENV-1..12. Метки: есть / частично / цель.

## Опора

- ADR-0001 (устав): порядок правоты Accepted ADR → канон → шаблоны/схемы.
- `docs/concept.md`: отложенные идеи «политика агентов», «проверка после развёртывания с откатом», «пресеты по типу проекта».
- Смежные области: `02-config` (переменные и секреты), `03-logging-errors` (поля логов), `06-ci-cd` (пайплайн и доставка), `09-data-model` (классы данных).
- Машинный источник правды: `registry/contours.yaml`, схема `schemas/contour-registry.schema.json`.

## Термины

| Термин | Что это | Пример |
|---|---|---|
| Контур | Физическое место запуска с одной зоной доверия | рабочий ПК `cnt` |
| Стадия | Роль в пути к продакшену: `dev`, `test`, `prod` | `dev` |
| Среда | Контур × стадия; единица адресации | `cnt.dev` |

## Правила

| Код | Правило | Метка |
|---|---|---|
| ENV-1 | Контуры описаны в одном реестре Angainor (`registry/contours.yaml`). Проза и проекции ссылаются на реестр, а не дублируют его. | цель |
| ENV-2 | Код контура: ровно три строчные латинские буквы. Код не меняется и не переиспользуется после вывода контура из эксплуатации. Код не несёт смысла, который может устареть (расположение, владелец, роль). | цель |
| ENV-3 | Стадия — отдельная ось с закрытым списком `dev` / `test` / `prod`. Среда записывается как `<контур>.<стадия>`, например `cnt.dev`. | цель |
| ENV-4 | Среда адресуется только своим кодом и везде одинаково: значение переменной `<PROJECT>_ENV`, поле `env` в логах, имя compose-проекта `<project>-<контур>-<стадия>`, тег деплоя, аргумент CLI. | цель |
| ENV-5 | Карточка контура содержит обязательные поля: роль, владелец, статус, стадии, зона сети и доступ, доставка (CI и способ), допустимые классы данных, хранилище секретов, права агентов. | цель |
| ENV-6 | Допустимые классы данных заданы списком для каждого контура. Всё, что не разрешено явно, запрещено. Класс данных проекта фиксируется в его pin и в `data-model.yaml`. | цель |
| ENV-7 | Путь продвижения — явный список переходов между средами с указанием способа доставки. Перехода, которого нет в списке, не существует. | цель |
| ENV-8 | Секреты живут в хранилище своего контура и не пересекают границ контуров. В репозитории только имена секретов, не значения. | цель |
| ENV-9 | Права агентов задаются на контур: список разрешённых инструментов и режим человека в контуре. По умолчанию запрещено. Здесь описана dev-time политика; runtime AgentPolicy (ENTAN) — отдельный документ. | цель |
| ENV-10 | Проект фиксирует среды, в которых живёт, и версию реестра в pin `docs/architecture/contours.yaml`. Проверка сверяет pin с реестром. | цель |
| ENV-11 | Для среды со стадией `prod` заданы проверка после выкатки и бэкап либо явный отказ с причиной. | цель |
| ENV-12 | Таблица контуров в README, раздел AGENTS.md «где что запускать, чего нельзя», матрица CI и список переменных — проекции реестра. Руками не правятся, дрейф ловит проверка. | цель |

## Зачем

Проверка здравого смысла: «написал → выкатил на `<код>`» должно однозначно определять цель, стадию, способ доставки, допустимые данные и права агентов. Без реестра эти знания живут в голове владельца и расходятся между проектами. Разделение контура и стадии не даёт смешивать «где» и «насколько боевое». Данные и права агентов вынесены в карточку, потому что именно они различают контуры по риску, а не по железу.

Основной CI — GitHub Actions с обёртками для GitLab/air-gap (рекомендация аудита, не реализовано). Префиксы переменных — открытый вопрос фазы 0.

## Как проверяется

Цель: `scripts/check_contours.py` (в ядре Angainor).

- реестр валидируется по `contour-registry.schema.json`;
- перекрёстные ссылки, которые JSON Schema не выражает: `allowed_data_classes` ⊂ `data_classes`, `promotion` ссылается на существующие среды, коды уникальны;
- код из предыдущего git-тега не исчезает и не меняет смысл (ENV-2);
- pin проекта валидируется по `contours-pin.schema.json` и сверяется с реестром (ENV-10);
- проекции пересобираются и сравниваются с закоммиченными (ENV-12).

Пока проверки нет, `check_canon_links.py` проверяет только связность кодов ENV-* с подробными файлами.

## Открытые вопросы

1. Незаполненные поля реестра (`TODO`): стадии, доступ, CI и способ доставки, хранилища секретов, допустимые данные, права агентов. Имя и код домашнего сервера (`cst`) и код Moexlab (`mxl`) — предложения.
2. Классы данных: стартовый список в реестре (`synthetic`, `public`, `own`, `licensed`, `employer`) — подтвердить или заменить. Отдельно решить, как учитывать лицензионные условия рыночных данных.
3. Префиксы переменных: ENV-4 предлагает один вход `<PROJECT>_ENV=<контур>.<стадия>` вместо префикса по коду контура. Согласовать с областью 02-config (CFG-*).
4. Различаются ли допустимые данные и права агентов по стадиям внутри одного контура. Сейчас поля на уровне контура.
5. Отдельные контуры для `test` или `test` — стадия на тех же серверах.
6. Доставка в Moexlab: образы идут по почте. Нужен формат бандла (манифест с версиями и sha256, проверка при приёме), решение по зависимостям без интернета (локальное зеркало, колёса в образе) и правило, кто и как подтверждает целостность.
6а. Адреса в реестре: публичный IP VPS (`prs`) лучше не хранить в репозитории, который может стать публичным. Варианты: оставить только приватные адреса, а публичные держать в инвентаре контура вне git.
7. ADR на схему именования контуров (Proposed), в одном ряду с форматом ADR и префиксами; номер назначить.
