# ADR-0002: Модель данных — одна спецификация DAMS, общий концептуальный слой, онтология Clavis над ним

**Статус:** Proposed  
**Дата:** 2026-11-09

Канон: [09-data-model.md](../canon/09-data-model.md), подробности — [09-data-model/](../canon/09-data-model/).

## Контекст

Каждое приложение должно иметь модель данных как каркас (DM-1). В экосистеме два места, где описываются понятия: moex-data-model (спецификация MOEX DAMS на LinkML, корпоративная концептуальная модель, модели решений) и Clavis (онтология в TTL, глоссарий в SKOS). В документации они друг на друга не ссылаются. Рядом с корпоративной моделью MOEX появляется модель данных PRODATA с теми же принципами: три уровня, общий концептуальный слой, решения по своим границам.

## Решение

1. **Одна спецификация.** Модели данных PRODATA описываются по той же спецификации MOEX DAMS, что и корпоративная модель. Своя спецификация — только если разойдётся метамодель; нехватка конструкции — минорная версия DAMS.
2. **Общий концептуальный слой из двух пакетов.** `moex-enterprise-conceptual-model` (корпоративные понятия) и `prodata-conceptual-model` (понятия платформы, которых нет в корпоративной модели; `depends_on` корпоративной). Каждое понятие определено ровно в одном пакете. Решения ссылаются на понятия любого из них.
3. **Решения по границам.** У каждого приложения — свой пакет `solution` с логическим и физическим уровнем.
4. **Онтология Clavis — уровень над концептуальной моделью.** Абстрактные классы с другой детализацией и целью. Понятие ссылается на класс онтологии через `external_class_refs` с видом соответствия; определение наследуется только при точном соответствии.
5. **Хранение.** Пакеты моделей — в репозитории моделей (ADR-058 D7 moex-data-model); приложение фиксирует версию и ревизию модели.
6. **Связь кода с моделью** — метки `element_id` из маленького пакета Norma без зависимостей `norma-nota` (метка, класс и поле; сбор меток; поставщик определений из снимка модели); проверка — в Angainor.
7. **Глоссарий** предметной области — вид на определения модели, собирается автоматически.
8. **Идентификаторы понятий PRODATA** — `dams:concept/prodata/<Name>`, внутри пространства `dams:`, без правки политики ADR-030.
9. **Файл фиксации модели в приложении** — YAML `docs/architecture/data-model.yaml`: репозиторий моделей, версия спецификации, пакеты с версией и ревизией.
10. **Миграции базы** пишутся как обычно; проверка в CI сверяет получившиеся таблицы и колонки с физической моделью. Генерация миграций из модели отклонена: генератора нет, а в PRODATA уже 50 миграций.

## Последствия

**Плюсы:**

- Ссылки между корпоративной моделью и моделью PRODATA работают напрямую, одни инструменты проверки.
- У каждого понятия один владелец и одно определение.

**Минусы и риски:**

- Изменения спецификации DAMS затрагивают и корпоративную модель, и PRODATA — нужны версии по ADR-051 и фиксация в пакетах.

## Рассмотренные варианты

| Вариант | Почему отклонён |
| --- | --- |
| Своя спецификация для PRODATA | метамодель та же; ссылки между моделями потребовали бы слоя отображений |
| Понятия PRODATA прямо в корпоративной модели | чужой владелец и процесс согласования; засоряет источник правды корпоративных понятий |
| Онтология Clavis как концептуальная модель | другой уровень детализации и другая цель; понятия модели данных конкретнее классов онтологии |
| Отдельные концептуальные модели у каждого решения | нет общего языка между системами — то, что модель должна устранить |
