# ADR-0005: Проверки git и CI — одна реализация, три места подключения

**Статус:** Accepted  
**Дата:** 2026-11-10

## Контекст

CI-1 требует, чтобы в CI не было логики, которой нет в локальной команде. Проверки работы с git (формат коммитов, имена веток, размер PR) надо выполнять и локально (git-хук), и в CI, а описывать нужно один раз. ADR-0004 дал поле `enforce` для событий агента; для git и CI оно пока не определено. Платформы (GitHub, GitLab) различаются форматом конфигурации, но не сутью проверок.

## Решение

1. **Три слоя.** Норма — в каноне (`docs/canon/06-ci-cd.md`), без привязки к платформе. Реализация — один Python-скрипт в `scripts/` Angainor. Подключение — поле `enforce` правила реестра.
2. **Расширение `enforce`.** К событиям агента добавляются события git (`pre-commit`, `commit-msg`, `pre-push`) и `ci` с полями `stage` (стадия) и `when` (`pull_request` или `push` в main/master). Ключ называется `when`, а не `on`, потому что в YAML 1.1 `on` читается как булево значение. В `args` доступны `{project}`, `{arg1}` (первый аргумент git-хука) и `{pr_range}` (диапазон коммитов PR).
3. **Инструменты копируются в проект** в `.angainor/tools/` с пометкой «generated» и могут импортировать только стандартную библиотеку (проверяет `check_rules.py`): в проекте нет зависимости от Angainor во время выполнения.
4. **Доставка git-хуков задаётся профилем:** `git_hooks: githooks` (по умолчанию) создаёт исполняемые файлы `.githooks/<событие>`; `git_hooks: pre-commit` вставляет блок между метками `# angainor:begin` и `# angainor:end` в существующий `.pre-commit-config.yaml`, не трогая остальное. Рукописный файл в `.githooks/` без пометки «generated» не перезаписывается — сборка сообщает об ошибке.
5. **CI-проекция (GitHub Actions).** Для каждой стадии генерируется `.github/workflows/angainor-<stage>.yml`, один шаг на привязку. Проверки, нужные в обязательных статусах, подключаются к защите ветки по имени job. Обёртка для GitLab (`.gitlab-ci.yml` с include) — следующая проекция, на источник она не влияет.
6. **Настройки платформы** (защита ветки, обязательные ревьюеры, права) не лежат в репозитории и проверяются отдельно: эталонный `platform/*.yaml` и скрипт `check_platform.py`, который сверяет его с API платформы по расписанию. Это отдельный шаг, до него такие пункты остаются «пожеланиями» без `check`.
7. **Включение хуков в рабочей копии** — действие разработчика, а не проекции: `git config core.hooksPath .githooks` либо `pre-commit install --hook-type commit-msg --hook-type pre-push`. Оно описывается в README проекта.

## Последствия

**Плюсы:** формат коммитов проверяется одинаково в хуке и в PR; новые проверки git подключаются полем в правиле; платформу можно добавить генератором.

**Минусы и риски:** проекция CI создаёт отдельные workflow рядом с рукописными, поэтому общее время CI растёт; в репозиториях с историей без Conventional Commits проверка диапазона PR падает на старых коммитах ветки; `core.hooksPath` несовместим с `pre-commit install` — поэтому режим выбирается профилем.

## Подтверждение

`check_rules.py` проверяет `stage`/`when` для `ci`, наличие инструмента и его импорты. `build_rules.py --check` ловит расхождения хуков, блока `.pre-commit-config.yaml`, workflow и копий инструментов. Тесты — `tests/test_rules_registry.py`.

## Рассмотренные варианты

- **Описывать CI-проверки прямо в workflow проекта.** Отклонено: логика расходится с локальной (нарушение CI-1) и дублируется по проектам.
- **Отдельный каталог `ci/` в Angainor как источник.** Отклонено по той же причине, что и в ADR-0004: второй реестр вместо поля правила.
