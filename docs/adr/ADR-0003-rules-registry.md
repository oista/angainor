# ADR-0003: Реестр правил для агентов — один источник, проекции по проектам

**Статус:** Accepted  
**Дата:** 2026-11-10

## Контекст

Правила для ИИ-агентов живут в проектах россыпью: 27 файлов `.cursor/rules/*.mdc` в пяти местах, три `.cursor/workflows.md`, два `AGENTS.md` разного назначения, три копии хука `normalize-plan-name.ps1`, дублирующие `.ps1`-скрипты выгрузки диалога. Разбор (09–10.11.2026) показал:

- одно и то же правило существует в 2–4 вариантах, которые уже разошлись (`plan-adr-link` с рабочими и с пустыми `globs`, три версии `docs-conventions`, три формата сообщений коммитов, два пути к `technical_quality_checks.md`);
- 17 из 23 разобранных правил включены всегда; в PRODATA это около 12 КБ контекста в каждом чате, из них заметная часть нужна лишь изредка;
- включить или выключить отдельное правило в одном проекте нельзя без правки файлов;
- значительная часть правил привязана к Cursor, Windows и PowerShell;
- про правила не известно, чем проверяется их соблюдение; в явном виде проверка названа лишь у нескольких.

Канон (`docs/canon/`) описывает нормы практики: что должно быть верно в проекте. Инструкции агенту — как действовать — в нём не заданы, а ADR-0001 не называет их частью Angainor.

## Решение

1. **Реестр правил** лежит в `rules/` в корне репозитория Angainor. Источник истины — он; файлы `.mdc`, `workflows.md` и копии хуков в проектах перестают быть источником.
2. **Файл на правило, как ADR.** `rules/shared/<область>/<ID>-<slug>.md` для общих правил и `rules/projects/<проект>/rules/<ID>-<slug>.md` для правил одного проекта. Файл состоит из YAML-шапки и трёх разделов: «Для агента» (короткие императивные указания; только он попадает в проекции), «Зачем», «Исключения». Шапка проверяется схемой `schemas/rule.schema.json`.
3. **Идентификаторы.** Общие — `ОБЛАСТЬ-N` (области канона `LAY`, `DOC`, `CI` и т. д., плюс новая область `AGT` — поведение агента). Проектные — `проект.ОБЛАСТЬ-N`. Номер не используется повторно. Статусы — `Proposed`, `Accepted`, `Deprecated`, `Superseded`, как у ADR.
4. **Связь с каноном и проверками.** Правило реестра ссылается на нормы канона (`norm`) и на проверку, которая ловит нарушение (`check`). Если проверки нет, реестр помечает правило как «пожелание». Канон отвечает «что должно быть верно», реестр — «как действует агент».
5. **Профиль проекта** — `rules/projects/<проект>/project.yaml`. Для каждого правила задаются `enabled` (вкл/выкл) и `activation` (`always`, `globs`, `on_request`), параметры, а при выключении — причина. Режим по умолчанию задаёт само правило, профиль может его переопределить. Личных переключателей поверх профиля нет. Профиль также закрепляет версию Angainor (тег) и может содержать карточку окружения (см. п. 11).
6. **Отступление от нормы — только через ADR проекта.** Правило, у которого есть `norm` (ссылка на канон), нельзя выключить в проекте простой причиной: требуется `waiver: ADR-NNNN` — Accepted ADR проекта, где названо правило и причина (как в README канона). Для правил без `norm` достаточно `reason`. Режим активации (`activation`) меняется свободно: это вопрос контекста, не нормы.
7. **Приоритет.** Умолчание правила < профиль проекта. Проект может добавлять свои правила, уточнять параметры, ужесточать (например, перевести правило в `always`) и менять режим активации. Выключить общее правило с `norm` или противоречить ему проектным правилом без `waiver` нельзя.
8. **Проекции генерируются** скриптом `scripts/build_rules.py` и коммитятся в проект с пометкой «generated by angainor, не править»:
   - `.cursor/rules/angainor-core.mdc` — одно правило `alwaysApply: true`, склеенное из всех включённых правил с режимом `always`;
   - `.cursor/rules/angainor-<ID>.mdc` — по файлу на правила с режимами `globs` и `on_request`;
   - блок в `AGENTS.md` между метками `<!-- angainor:begin -->` и `<!-- angainor:end -->`; рукописный текст вне меток сохраняется;
   - `.cursor/hooks.json` для правил с исполняемой частью.
   
   Рукописные правила вне реестра в проектах не допускаются. `.cursor/workflows.md` выводится из обращения; его содержимое разбирается на правила.
9. **Бюджет «всегда включённого» — в токенах.** В профиле задаётся `always_on_budget_tokens`; сборка падает, если склеенное `angainor-core.mdc` и always-блок `AGENTS.md` его превышают. Способ подсчёта единый и фиксируется в `check_rules.py` (до появления токенайзера — приближение по числу символов); байты не используются, так как русский и английский текст весят по-разному.
10. **Наглядные страницы** генерируются в `rules/`: `RULE-INDEX.md` (все правила, статусы, проверки), `RULE-MATRIX.md` (правило × проект, режим), и `rules/projects/<проект>/RULES.md` (что действует в проекте и сколько «весит»).
11. **Карточка окружения.** Сведения вида «как запустить lint, тесты и приложение, какие у среды ограничения» — не правила: у них нет режима активации и переключателя. Они задаются в профиле (`environment`) и проецируются в `AGENTS.md` отдельным блоком. Так заменяется рукописный раздел «Cursor Cloud specific instructions» в ENTAN.
12. **Инструменты на Python (LAY-4).** `scripts/build_rules.py`, `scripts/check_rules.py` — реестр; `tools/plan_name_hook.py`, `tools/export_dialog.py` — утилиты, которые запускаются в проектах и заменяют `.ps1`-копии. PowerShell допускается только как тонкая обёртка.
13. **Подключение проектов** — по одному, отдельными PR (CI-5), начиная с пилота. Состав первого набора (14 общих и 7 проектных правил), таблица переноса и фазы — в приложенном предложении (проект Claude «angainor», `rules-registry-proposal-2026-11`); при принятии ADR они переносятся в `rules/README.md`.

## Последствия

**Плюсы:**

- Одно место для правок; правило не расходится по копиям.
- Каждое правило можно включить, выключить или перевести в другой режим для конкретного проекта; видно общую картину в матрице.
- Контекст агента под контролем бюджета, а не растёт с числом правил.
- Реестр не привязан к одному инструменту: Cursor и `AGENTS.md` — проекции, Claude Code и другие добавляются генератором.
- Правила без проверки видны сразу, это подталкивает превращать их в проверки.

**Минусы и риски:**

- Новый код, который нужно сопровождать (генератор, схемы, проверка реестра).
- Проекции приходится коммитить в каждый репозиторий; нужна проверка «совпадает с тем, что даёт генератор».
- Изменение общего правила касается всех проектов. Поэтому проект закрепляет версию Angainor (тег) в профиле, `build_rules.py --diff` показывает изменения проекций до применения, у правила есть `since`, а удаляется правило не сразу: сначала `Deprecated` (`deprecated_since`) минимум на один выпуск.
- Формат `.mdc` и работа режимов Cursor могут измениться; проекции придётся адаптировать.
- Правила, у которых нет исполняемой проверки, остаются только указаниями модели.
- Перенос требует аккуратности: часть содержимого `workflows.md` и `.mdc` пересказывает ADR и должна уйти в ссылки, а не копироваться.

## Рассмотренные варианты

| Вариант | Почему отклонён |
| --- | --- |
| Правила и профиль в каждом проекте, Angainor даёт только шаблон | возвращает расхождение копий; нет общей картины и общей матрицы |
| Один большой YAML-файл без отдельных файлов | трудно читать человеку и ревьюить диффом; не похоже на ADR, нет места для обоснования |
| Добавить область «Агенты» в канон (`docs/canon/`) и не заводить реестр | смешивает нормы с инструкциями агента; нет переключателей по проектам и генерации проекций |
| Оставить `.mdc` и `workflows.md` как есть, только почистить | дубли вернутся; нет переключателей; привязка к Cursor остаётся |

## Подтверждение

`scripts/check_rules.py` (тесты: `tests/test_rules_registry.py`): шапки правил и профилей проходят схемы `rule.schema.json` и `project-profile.schema.json`; идентификаторы уникальны, имя файла и расположение согласованы со `scope`; у правила непустой раздел «Для агента»; `norm` ссылается на существующие коды канона; у каждого выключенного правила с `norm` есть `waiver`; режимы `globs` и `on_request` обеспечены `globs` и `triggers`; бюджет always-on (в токенах) в норме; фразы-триггеры не пересекаются внутри проекта; закреплённый тег Angainor существует. С `--repos-root` дополнительно проверяется, что `check` проектных правил существует в репозитории проекта, а `waiver` указывает на Accepted ADR.

`scripts/build_rules.py --check` подтверждает, что проекции в проектах совпадают с результатом генератора. Не реализовано и остаётся следующей итерацией: запрет рукописных `.mdc` вне реестра и генерация `.cursor/hooks.json`.
