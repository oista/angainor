## 1. Общая картина

- **Три слоя.** Глобальный (процесс работы с самим Cursor: фиксация диалогов и планов), проектный «словарный» (восемь почти одинаковых правил в PRODATA) и проектный «инженерный» (CI, целостность БД, документация, серии PR, docker-образы).
- **Хорошая основа.** Правила в основном конкретные: есть триггер, алгоритм, запреты, ссылка на скрипт или ADR. Это видно по `ci-watch`, `referential-integrity`, `multi-pr-series`, `loop-contract`.
- **Главная проблема — масштабирование.** 17 из 23 правил `alwaysApply: true`, около 21 КБ в каждом чате (порядка 6–7 тыс. токенов, оценка). Из них заметная часть нужна только в редких ситуациях.
- **Второе — копипаст вместо источника истины.** Восемь словарных правил на 90% совпадают, три правила про фиксацию диалогов пересекаются, а нормы из ADR пересказаны внутри правил (риск расхождения).
- **Третье — привязка к одной среде.** Windows, PowerShell, `py -3.11`, self-hosted runner «Centurion», Cursor. Это конфликтует с канонным LAY-4 (логика проверок на Python, `.ps1` только как тонкая обёртка) и с идеей Angainor «один реестр → проекции для разных инструментов».
- **Проверка соблюдения названа лишь в части правил:** `referential-integrity`, `loop-contract`, `design-system`, `plan-adr-link`, частично `user-docs`. Для остальных это поведенческое пожелание без проверки, то есть ровно то, что Angainor называет «решение без проверки — пожелание».

## 2. Глобальные правила (`~/.cursor/rules`)

### dialog-fixation.mdc (830 Б, alwaysApply)

Триггеры «зафиксируй / wrap / export dialog / сохрани диалог»: не пересказывать диалог, не писать markdown-заметку, напомнить про Save to Workspace для планов, запустить `scripts/export-cursor-dialog.ps1` (если есть) → `docs/dialogs/raw/`, ответить только путём.

Хорошо:
- Прямой запрет на пересказ — агент не «улучшает» то, что должно быть сырым архивом.
- Безопасный выход: «если скрипта нет — скажи и остановись».
- Ответ только путями — минимум шума.

Плохо:
- Глобальное правило знает про конкретный скрипт, который есть не во всех репозиториях. В канонном шаблоне (`templates/scripts/`) его нет.
- Только PowerShell/Windows. Не переносимо и расходится с LAY-4.
- Сырые диалоги кладутся в репозиторий (`docs/dialogs/raw/*.jsonl`). Риск попадания секретов, персональных данных и большого объёма в git; в канонном `.gitignore` и правилах об этом ничего не проверял.
- Пересекается с проектным `session-notes.mdc` (см. ниже).

### plan-fixation.mdc (706 Б, alwaysApply)

При фиксации копировать планы только из `{repo}/.cursor/plans/` (после Save to Workspace), не из глобальной кучи, в `docs/plans/` с нормализацией имени `{Project}: …`. Не писать пересказов планов руками.

Хорошо: чётко отделяет «рабочие» планы репозитория от глобальной свалки; тот же скрипт, нет второго механизма.
Плохо: правило не самостоятельное — работает только вместе с dialog-fixation и тем же скриптом; три правила про одну операцию вместо одного.

### plan-naming.mdc (695 Б, alwaysApply)

Перед созданием плана имя = `{Project}: {Короткая тема}`, где Project — последний сегмент пути корня рабочей области. Примеры ✅/❌.

Хорошо:
- Честно написано: «платформа не принуждает, это мягкое правило». Это единственное правило, которое прямо признаёт, что без хука оно только пожелание.
- Примеры правильного и неправильного.

Плохо:
- Глобальное правило ссылается на хук `.cursor/hooks/normalize-plan-name.ps1` «в этом репозитории» и использует `Isthmus` как пример. Знание одного проекта просочилось в глобальный уровень.
- Опора на хук, который я не видел, и на «best-effort» срабатывание.

## 3. PRODATA (moex-prodata-platform, 13 правил)

### Словарные правила (8 файлов)

`archpolicy-structures` (по globs, не always), `domain-structures`, `eval-structures`, `lifecycle-structures`, `metric-structures`, `ontology-structures`, `process-structures`, `repo-structures` (все always). Размер 735–1 067 Б каждое, вместе ~7,5 КБ.

Шаблон у всех один: прочитай `docs/<область>/<область>_structures.md` → используй только английские термины оттуда → не изобретай синонимы без одобрения → нет термина: предложи, дождись OK, добавь в файл, потом используй → поля внутри сущностей — не новые сущности → (иногда) «не путай X с Y».

Хорошо:
- Сама идея верна: единый словарь (ubiquitous language), агент не плодит синонимы. Это прямо отвечает проблеме «ИИ придумывает названия».
- Процедура добавления термина (предложить → OK → файл → использовать) — понятный контроль.
- Пункт «поля не сущности» снимает частую путаницу.
- Строки «не путай» — самое ценное: `Judge` в archpolicy ≠ eval `LLM Judge`; `Domain` ≠ `Metric Domain`/`Domain Pack`; `Index Version` ≠ git ref; не использовать `status_changed` как бизнес-контракт; `Local Ontology` ≠ `Reference Ontology`.

Плохо:
- **Восемь копий одного текста.** Пункты 1–5 слово в слово; меняются только имя файла и примеры. Любое улучшение придётся вносить восемь раз.
- **Семь из восьми always-on**, хотя каждое нужно только когда речь о своей области. `archpolicy-structures` сделан иначе (globs) — непоследовательно.
- Ценные «не путай» тонут в шаблонном тексте; в `ontology-structures` в словарное правило попал архитектурный факт («Owner OWL = Clavis; Groma — только BFF, без PG-хранилища онтологий») — его место в ADR/контуре, не в правиле о словаре.
- Нет проверки: никто не сверяет, что код и документы используют только термины из `*_structures.md`.
- **Конфликт с каноном:** DOC-4/DM-4/DM-5 решили, что термин предметной области — определение элемента модели, глоссарий собирается из модели, а `docs/glossary.md` — только технические термины. Тем временем в экосистеме уже четыре места для терминов: модель, `docs/glossary.md`, `*_structures.md`, `docs/user/glossary.yaml`.
- Язык «English name» + русские документы — не оговорено, где живёт русское название.

### ci-watch.mdc (2 125 Б, alwaysApply)

После `git push` / `gh pr create` агент сам следит за GitHub Actions: список запусков, на `main` — оба workflow (`quality` и `deploy`), при падении — хвост лога, минимальный фикс, один push, не больше 2–3 циклов, потом эскалация. Деплой на self-hosted Centurion: инфраструктурные сбои — коротким отчётом.

Хорошо:
- Лучшее по конкретике: алгоритм по шагам, лимит итераций, эскалация.
- Сильные запреты: не менять workflow, чтобы «позеленело»; без force-push; без merge без просьбы; локальный `compose up` не заменяет зелёный `deploy`.
- «Только хвост лога» экономит контекст.
- Граница автономии ясна: чинить причину можно, трогать правила игры нельзя.

Плохо:
- **Внутреннее противоречие:** в шаге 1 захардкожен `oista/prodata-platform`, а рядом сказано «бери владельца и репо из `git remote`, никогда не хардкодь `moex-enterprise-analyst`». Это след копирования из другого репозитория.
- Ссылается на субагента `ci-investigator` и навык Autopilot, которых в глобальной папке `agents` нет (она пуста); где они лежат — не знаю.
- Специфика инфраструктуры (Centurion, `scripts/gha-deploy.ps1`) смешана с общим алгоритмом.
- Это процедура, а не норма; always-on для ситуации «после push» дорого — естественнее навык или команда.
- Нигде не сказано, когда агенту вообще можно делать push (разрешение живёт только «по умолчанию»).

### design-system.mdc (1 069 Б, globs)

Пять принципов UI для `platform_web`: деревья свёрнуты, единые кнопки, разделённые панели, никаких инлайновых цветов, одинаковый вид списков операций. Перед коммитом — `check_design_conventions.py`.

Хорошо: правильно ограничено globs; правила проверяемые («нет `style="color"`», нет Tailwind `bg-red-*`); названа проверка.
Плохо: команда `py -3.11` — только Windows-лаунчер; проект-специфично (останется в PRODATA или в пресете веб-интерфейса, но не в общем канонном наборе).

### plan-adr-link.mdc (490 Б, globs пустой)

В YAML-шапке плана — `adr: ADR-NNNN`; фича начинается с заглушки ADR с отклонёнными вариантами; включённые модули ссылаются на принятый ADR (`check_adr_integrity.py`).

Хорошо: воплощает связку «решение → план → код»; названа проверка.
Плохо: `globs:` пустой и `alwaysApply: false` — правило срабатывает только по усмотрению модели и на практике, скорее всего, не подключается при создании плана. Дублирует DOC-8/DOC-6 и шаблон `templates/docs/plans/template.md`.

### referential-integrity.mdc (1 124 Б, alwaysApply)

Колонка, ссылающаяся на другую сущность, — настоящий `FOREIGN KEY`; отсутствие — `NULL`, не `DEFAULT ''`; не пополнять `DEBT_ALLOWLIST`; исключения только в `EXCEPTION_COLUMNS` с причиной; составной родитель — составной FK. Пример bad/good SQL. Запуск `check_referential_integrity.py` (в т. ч. `--live`).

Хорошо:
- Образец того, как должно быть: правило → скрипт → список долгов, который только уменьшается.
- Пример плохо/хорошо; запрет `DEFAULT ''`.
- Универсальная идея, годится как правило канона.

Плохо: always-on, хотя нужно при работе с миграциями и схемой БД (подходят globs); список имён частично живёт в скрипте, не в правиле — две точки правды; привязано к Postgres и схеме `platform.*`.

### session-notes.mdc (839 Б, alwaysApply)

То же, что `dialog-fixation`: не пересказывать, не читать транскрипт, запустить `.\scripts\export-cursor-dialog.ps1`, ответить путём. Плюс опции `-Name`, `-Id`, `-All`.

Хорошо: опции скрипта описаны; прямой запрет читать транскрипт.
Плохо: полностью пересекается с глобальным `dialog-fixation` (одни и те же триггеры, одно действие), но не знает про планы; название «session-notes» вводит в заблуждение — правило как раз запрещает писать заметки. Когда загружены оба, агент видит два неполных алгоритма.

## 4. moex-enterprise-analyst (4 правила)

### docs-conventions.mdc (1 033 Б, globs `docs/**/*.md`)

Новый публичный термин → запись в `docs/glossary.md` в том же изменении; таблицы GFM выровнены по самой широкой ячейке (`mdformat docs/`); в папках серий (`docs/adr/`, `docs/design-notes/`) обязательны `template.md` и индекс.

Хорошо: правильно ограничено globs; ровно совпадает с DOC-4/DOC-5, то есть уже подтверждённая практика.
Плохо:
- Канонический источник указан относительным путём за пределы репозитория: `../../norma/docs/docs-conventions.md` — ломается вне монорепо-раскладки и в CI.
- Ссылка на `.cursor/workflows.md` §2.2 (не видел).
- Требование выровненных таблиц не проверяется автоматически. Заметка: в самом angainor (`README.md`, `docs/concept.md`) таблицы не выровнены, то есть канон сам не следует этому правилу.

### loop-contract.mdc (1 445 Б, globs на `agent/**`, `domain_packs/**` и др.)

При правке механизма из `agent/contract/catalog.yaml` (или добавлении мутации `system_prompt`/`messages`/`tools`/`loop_control`/`final_content`): обновить каталог, реестр инвариантов, фикстуры и мета-тесты в том же изменении; прогнать `loop_conformance.py` и `pytest tests/contract/`. Класс B — только наблюдение; **починка засчитывается как нарушение**; не вшивать `/no_think`.

Хорошо:
- Очень сильная идея: каталог вмешательств + реестр инвариантов + проверка соответствия — это почти готовое ядро будущего «реестра инвариантов» Angainor.
- «Автоисправление не считается успехом» — зрелое требование.
- Правильно ограничено globs; названы проверки.

Плохо: в одном правиле смешаны общий процесс («обновляй каталог в том же изменении») и сиюминутные продуктовые решения (запрет `/no_think`, `extract_final_answer`); вторые должны быть инвариантами с проверкой, а не фразой в правиле. Привязано к ADR-0021.

### pack-docker-image.mdc (1 356 Б, alwaysApply)

На фразы «собери образ», «pack docker image» и т. п.: запустить `scripts/pack_docker_image.ps1`, дождаться, ответить путями артефактов, размером и SHA256; режим «контур-обновление» с `-Contour -ParentTag`. Артефакты и колёса не коммитить.

Хорошо: чёткие границы («не править `.env`, не пересказывать Dockerfile, показать ошибку как есть»); связано с CI-6 (air-gap).
Плохо: по сути команда, а не правило, при этом always-on; русские триггер-фразы; только `.ps1`; жёсткая зависимость от соседнего репозитория `../norma/packages/norma-libella`.

### repo-layout.mdc (799 Б, alwaysApply)

Новые каталоги верхнего уровня только с явным одобрением и после «ворот»: строка в `decision-log.md` (или ADR), обновить README §5, `architecture.md` и инвентарь в design-note. Новый код — в существующие пакеты слоёв. Артефакты (`logs/`, `eval_output/`, `reports/`) не коммитить.

Хорошо: хорошая идея ворот; согласуется с LAY-1 (белый список корня); повод для автоматической проверки.
Плохо: проверки нет (в PRODATA для этого есть `check_repo_hygiene.py` — см. канон); три обязательные правки на каждый каталог — тяжело; из правила следует плоская раскладка (`tools/`, `agent/`, `schemas/` в корне), что не совпадает с LAY-2 (код только в `src/`). Это вывод по тексту правила, а не по самому репозиторию.

## 5. moex-data-model (3 правила)

### multi-pr-series.mdc (2 443 Б, alwaysApply)

Для серии PR-0…PR-N: одна тема на PR; разные коммиты/ветки, не «всё сразу»; PR-0 не трогает схемы и `generated/`; не перескакивать окно депрекации; изменение схемы и миграция данных не смешиваются; готовый прототип архивируется в `wip/` и перерезается заново. Документированное исключение для финального PR-5 (удаление) со ссылками на ADR-048/049. Указания пользователя или плана главнее.

Хорошо:
- Лучшее поведенческое правило набора: причины понятны, исключение описано прямо, есть явное «пользователь главнее».
- Мысль «зелёный итог не доказывает промежуточные состояния» — редкая и ценная.
- Совпадает с CI-5 (схема и данные разными PR) — проверенная практика, достойная канона.

Плохо: общая дисциплина и исключение конкретных ADR в одном тексте; упомянуты `make check`, `ruamel.yaml`, `generated/` — детали проекта; always-on, хотя нужно только при серии (естественнее навык или правило по запросу); проверки нет.

### publication-section-profiles.mdc (3 301 Б, globs на `publish.yaml` и др.)

Правила для `PublicationModule`: `profile`, `kind` из `PublicationSectionKind`, `type` ортогонален, обязательные/рекомендуемые/запрещённые секции по профилям, `satisfies:` по ADR-019, `instance_of:` для карточек экземпляров.

Хорошо: правильно привязано к файлам; очень конкретно.
Плохо: **пересказ норм ADR-016/019/020/024/027/028 внутри правила.** При изменении ADR правило устареет, и именно оно будет читаться первым. Нет указания, какой проверкой это контролируется. Чисто проектное — в общий канон не идёт.

### user-docs.mdc (4 367 Б, alwaysApply)

Держать `docs/user` в актуальном состоянии (ADR-057): список случаев, когда страницу обновлять в том же PR; запись в `descriptions.yaml`, `glossary.yaml`, поле `sources`; `not_covered` в `toc.yaml`; пересборка `docs/user/index.html` (`make user-docs`). Правило языка: сначала обычное русское объяснение, термин со ссылкой на глоссарий, четыре вопроса на страницу; черновик агента остаётся `draft: true`, **дату `verified_at` ставит человек после сверки**.

Хорошо:
- Паттерн «агент не ставит отметку проверки» — настоящий контроль человека без лишнего текста.
- «Сегодняшнее число сверкой не является» — предотвращает самую частую ложную отметку.
- Прямо оговорено, чего автоматика не проверяет (язык, четыре вопроса).
- Идея «обновляй документ в том же PR» ровно соответствует DOC-1/DOC-3.

## 6. Сквозные наблюдения

### Сильные стороны набора

1. Конкретность: триггер → шаги → запреты → что отвечать.
2. Явные границы автономии (ci-watch, pack-docker, multi-pr-series, user-docs).
3. Три образца «правило + скрипт + ratchet»: `referential-integrity`, `loop-contract`, `design-system`.

### Слабые стороны

1. **Раздутый always-on** (17 из 23, ~21 КБ). Расходует контекст в каждом чате и разбавляет важное.
2. **Копипаст:** 8 словарных правил; 3 правила про фиксацию; следы переноса между репозиториями (`oista/prodata-platform` vs «никогда не хардкодь moex-enterprise-analyst»).

## 12. Хуки

`hooks.json` в ENTAN и Clavis: на `afterFileEdit` и `postToolUse` (`Write|EditNotebook`) запускается `normalize-plan-name.ps1` через `powershell.exe -ExecutionPolicy Bypass`, таймаут 15 с.

Что делает скрипт: читает JSON хука, находит `*.plan.md` в `.cursor/plans`, добавляет к `name:` префикс проекта и переименовывает файл (`{project}_{slug}_{id}.plan.md`). Всегда завершается с кодом 0 и пустым `{}` (fail-open). Копии в ENTAN и Clavis почти одинаковы; различаются запасным именем проекта и тем, что в Clavis `cavis` заменяется на `clavis`.

Хорошо: единственный пример **исполняемого** механизма вместо уговора модели; fail-open не блокирует работу; решает проблему, которую правило `plan-naming` честно называет «мягкой».
Плохо:
- Есть только в двух репозиториях из четырёх, а глобальное правило `plan-naming` действует везде: в PRODATA и moex-data-model именование держится только на уговоре.
- PowerShell и Windows; процесс запускается на каждое изменение любого файла.
- `-ExecutionPolicy Bypass` и переименование файлов на лету без журнала.
- Скрипт скопирован, а не подключён из общего места.
