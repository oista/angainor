# AGT-6: Следить за CI после push

## Для агента

После `git push` или `gh pr create` по этому репозиторию, а также по фразам «проверь CI», «посмотри Actions», «почему упал CI» сам смотри GitHub Actions, не жди напоминания.
1. Список запусков ветки: `gh run list --branch <ветка> --limit 5`; владельца и репозиторий возьми из `git remote get-url origin`.
2. На `main` дожидайся всех workflow: {{main_workflows}}. Успех — только когда все `success`.
3. При падении читай хвост лога: `gh run view <id> --log-failed`, не весь лог.
4. Чини причину минимальным диффом; перед push прогони локально узкую проверку упавшего шага. Один push, затем снова жди результат.
5. Не меняй workflow ради зелёного статуса, не делай force-push и merge без просьбы.
6. Не больше 3 циклов «исправление → push → ожидание» за сессию, потом остановись и сообщи.
7. Сбои инфраструктуры деплоя (занятые имена контейнеров, гонки миграций, Docker) — короткий отчёт, без правки YAML деплоя. {{deploy_note}}
Локальный запуск compose не заменяет зелёный `deploy`.

## Зачем

Перенос `ci-watch` PRODATA без захардкоженного репозитория и без ссылки на несуществующего `ci-investigator`.

## Как проверяется

Пожелание.

## Исключения и особенности проектов

Параметры: `main_workflows`, `deploy_note` (особенности деплоя проекта).
